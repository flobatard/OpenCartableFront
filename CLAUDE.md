# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projet

Front Angular 22 d'**OpenCartable**, plateforme pédagogique auto-hébergée (AGPLv3) : un prof authentifié (OIDC/Zitadel) compose des cours, les élèves les consultent via liens publics sans compte. Cadrage produit : `Descriptions.md`. Design system (source de vérité UI) : `DESIGN_SYSTEM.md`.

## Commandes

Node est géré par nvm ; dans un shell non-interactif, npm n'est pas sur le PATH :

```bash
export PATH="$HOME/.nvm/versions/node/v26.3.0/bin:$PATH"
```

```bash
npm start                              # dev server (4200)
npm run build                          # build prod + prerender de la home
npm test                               # vitest (jsdom)
npm test -- --include src/app/core/theme/theme.service.spec.ts   # un seul fichier
npm test -- --filter "ThemeService"    # par nom de suite/test
npm run serve:ssr:OpenCartableFront    # sert dist/ via Express (4000)
docker compose up --build              # conteneur SSR (4000)
```

Après tout changement touchant SSR/i18n/prerender, vérifier que `dist/OpenCartableFront/browser/index.html` contient bien le texte français rendu (pas de chaînes vides) : c'est le symptôme d'une régression du préchargement Transloco.

## Architecture et invariants

**Zoneless** (pas de zone.js — défaut Angular v22) : tout état partagé est exposé en **signaux** ; les souscriptions rxjs écrivent dans des signaux. Ne jamais ajouter `provideZoneChangeDetection`.

**Trois modes de rendu** (`src/app/app.routes.server.ts`) : `/` prerendered au build, `/auth/callback` client-only (il manipule URL et storage), `**` SSR. Toute nouvelle route doit choisir son mode ; une route qui touche `window`/`localStorage` sans garde ne peut pas être SSR/prerender. Une route protégée par `authGuard` doit être en `RenderMode.Client` (le guard renvoie `false` au serveur — jamais authentifiée au SSR, donc jamais prerendable) : cf. `:lang/subjects`.

**Réutilisation des routes** (`core/routing/remount-on-param-change.strategy.ts`, fournie dans `app.config.ts`) : comportement Angular par défaut, sauf pour les routes marquées `data: { remountOnParamChange: true }` — les deux éditeurs `courses/:id/blocks/:blockId` et `courses/:id/modules/:moduleId` — qui sont **détruites/remontées quand leurs params changent** (le flush d'autosave du `ngOnDestroy` tourne, puis l'init). Raison : ces pages lisent leurs params en **snapshot**, or une citation `oc-block:` du panneau assistant peut naviguer d'un éditeur de bloc vers un autre (même route, autre `blockId`) — sans le flag, l'instance réutilisée garderait un id périmé. Les composants conçus pour survivre à un changement de param (`DocsShell`, `StudentBlock` — paramMap observé) ne posent **pas** le flag ; un changement de query params seuls ne remonte jamais rien.

**Couche données HTTP** : `SubjectService` (`src/app/core/subjects/`) est le patron des accès API. Un seul `HttpClient.get` par ressource, mis en cache via `shareReplay({ bufferSize: 1, refCount: false })`, état exposé en signaux (`tree`/`loading`/`error`) alimentés par la souscription rxjs. Le Bearer Zitadel est attaché **automatiquement** par l'intercepteur d'`angular-oauth2-oidc` à toute requête sous `environment.apiUrl` (`resourceServer.allowedUrls` dans `app.config.ts`) — ne pas ajouter de header manuel ; `apiUrl` inclut déjà `/api`. Fetch déclenché côté navigateur uniquement (guard `isPlatformBrowser`). Les helpers purs de l'arbre (recherche, chemin d'ancêtres, aplatissement, lignes de treeview) vivent dans `subject.utils.ts`, testés isolément. `EducationLevelService` (`src/app/core/education-levels/`) est le second exemplaire du patron (mêmes signaux + cache) ; ses helpers minimaux vivent dans `education-level.utils.ts` — on ne généralise **pas** `subject.utils.ts` pour ne pas coupler les deux pickers. Les libellés métier (`name` des matières et des niveaux d'étude) viennent de l'API et **ne passent pas** par l'i18n.

`UserProfileService` (`src/app/core/users/`) est la variante **mutable** du patron : pas de `shareReplay` figé mais un signal `profile` source de vérité, une **promesse en vol partagée** (`ensureLoaded()` — callback et guard n'émettent qu'un GET, invalidée sur erreur pour permettre le retry), les mutations remplacent le signal (`saveProfile()` : le `PUT /users/me/profile` sert d'onboarding initial **et** d'édition de profil, sémantique remplacement, pas de refetch) et un `effect` purge le profil quand `AuthService.isAuthenticated()` retombe. La logique du formulaire de profil (forme du FormGroup typé, règles de cohérence, mapping payload, complétude) est **factorisée en helpers purs** dans `core/users/profile-form.ts`, partagés par l'onboarding et la page profil — les templates, eux, restent distincts (stepper vs page à plat). Piège d'ordre : `patchFormFromProfile` pose `system` avant les blocs, sinon la cohérence câblée viderait les niveaux patchés.

**Espace cours** (`core/courses/` + `features/courses/`) : `CourseService` est la variante mutable **multi-ressources** du patron — signaux `list`/`detail` sources de vérité **refetchés à chaque entrée de page** (pas de `shareReplay` : données mutables), mutations async (`createCourse`, `addBlock` — qui porte un méta titre/description optionnel —, `deleteBlock`, `reorderBlocks`, `updateBlockContent`, `updateBlockMeta`, `updateBlockResource` — PATCH dédié `{resource_id}` des blocs `document`, jamais mêlé au content ni au méta — et son miroir `updateBlockModule`, PATCH dédié `{module_id}` des blocs `module`) qui patchent localement le signal `detail` (depuis la réponse du back, **sauf `reorderBlocks` qui est optimiste** : il réordonne le signal **avant** le PUT et laisse l'appelant recharger sur erreur ; `#patchDetail` ne s'applique que si le détail affiché est le cours muté), purge à la déconnexion. **Quatre types de blocs, tous créables** : `text`, `exercise`, `document` (pont nullable vers une ressource de la bibliothèque — `resource_id` en colonne ; supprimer la ressource supprime le bloc, FK CASCADE côté back) et `module` (pont nullable vers un module interactif de la bibliothèque de modules — `module_id` en colonne ; supprimer le module supprime le bloc, FK CASCADE côté back). Les blocs portent `title`/`description` facultatifs (tous types, distincts du `content`). Helpers purs du formulaire de création dans `core/courses/course-form.ts` (motif `profile-form.ts`) ; ceux du méta titre/description d'un bloc dans `core/courses/block-meta-form.ts`, **partagés par la modale de création et l'éditeur** ; ceux du contenu document (`buildDocumentForm`, `payloadFromDocumentContent` — normalisation avec replis —, `payloadFromDocumentForm`) dans `core/courses/document-form.ts`. Pages : liste `courses` (cartes, badges matières/niveaux résolus dans les arbres — id inconnu = pas de chip), création `courses/new` (**déclarée avant** `courses/:id`, matching en ordre ; picker de niveaux filtré par le `school_system` du profil), page cours `courses/:id` à **quatre onglets Blocs | Ressources | Modules | Aperçu** (tablist APG au motif `markdown-field`, ids ARIA par compteur de module ; panneaux en `@if` — pas de Monaco ici, rien à préserver ; **cyclage clavier ←/→ par index via `TAB_ORDER`** ; onglet actif reflété dans `?tab=` — Blocs = défaut donc param retiré, `resources`/`modules`/`preview` sérialisés — via `router.navigate([], {replaceUrl: true})`, deep-linkable ; le retour d'éditeur retombe sur Blocs) — onglet Blocs : liste = titre en gras + description ; **création via une modale** `block-create-dialog` saisissant titre/description, puis **redirection** vers l'éditeur du bloc créé ; « Modifier » sur **tous** les types ; **réordonnancement par glisser-déposer (poignée `grip-vertical` + `cdkDragHandle`, `@angular/cdk/drag-drop`) ou flèches ↑/↓ discrètes — poignée aussi opérable au clavier (↑/↓/Début/Fin), via helper pur `moveIdTo` ; le câblage DnD ne binde pas `cdkDropListData` ni n'appelle `moveItemInArray` (le signal `detail` reste seule source de vérité)** ; suppression en deux temps sans modale, désarmée au blur — onglet Ressources : composant `CourseResources` (voir ci-dessous) dont l'output `(deleted)` fait recharger le détail du cours par la page (les blocs document pointeurs ont été supprimés en cascade par le serveur) — onglet Modules : composant `CourseModules` (voir **Bibliothèque de modules interactifs**), même contrat `(deleted)` — onglet Aperçu : composant `CoursePreview` (voir ci-dessous), **vue élève** du cours entier —, éditeur de bloc `courses/:id/blocks/:blockId`, éditeur de module `courses/:id/modules/:moduleId`. Toutes protégées `[authGuard, onboardingGuard]` + `RenderMode.Client`, params lus en snapshot (pas de `withComponentInputBinding` dans ce projet). Le header porte le lien « Mes cours » quand la session est ouverte.

**Export/import de cours** (`core/courses/course-transfer.utils.ts` + `features/courses/course-import-dialog/`) : l'**export** (bouton « Exporter » de l'en-tête de la page cours, poussé à droite par `margin-left: auto`) télécharge l'archive `.zip` du back via `CourseService.exportCourse` — **premier `responseType: 'blob'` du projet** : l'endpoint exige le Bearer (URL sous `apiUrl`), donc pas de `window.open` comme pour les URL S3 présignées — puis `downloadBlob` (`URL.createObjectURL` + `<a download>` éphémère, browser-only, stubs dans les specs : jsdom n'implémente pas `createObjectURL`) sous un nom calculé **côté front** par `courseExportFilename` (le `Content-Disposition` du back n'est pas lisible sans `expose_headers` CORS — assumé) ; échec → toast (message traduit par l'appelant, motif `CourseShare.copy()`). L'**import** (bouton « Importer » du header de « Mes cours », groupé avec le CTA dans `.course-list__actions`) ouvre `CourseImportDialog` — `<dialog>` natif au motif `block-create-dialog`, mais qui appelle le service **elle-même** (motif `CourseResources`) : pré-contrôle 500 Mo (`MAX_IMPORT_BYTES`, miroir de `TRANSFER_MAX_ZIP_BYTES` back), puis `CourseService.importCourse` — **premier POST `FormData` multipart du projet** : ne JAMAIS poser de `Content-Type` manuel, le navigateur écrit le boundary — dont la progression alimente le signal **`importState`** (`idle|uploading|processing|error` + `progress`, purgé à la déconnexion ; `processing` = corps envoyé, le back parse et pousse vers S3) ; erreurs par statut (413/422/503 → clés dédiées, sinon générique), fermeture bloquée pendant l'envoi, puis toast succès, insertion du cours en tête de `list` et **navigation vers le cours recréé** (nouveaux ids — le back remappe aussi les références `oc-resource:`/`oc-module:` du markdown). Tout spec montant une page qui embarque la modale doit fournir `importState`/`importCourse` dans son mock de `CourseService`. Clés i18n `courses.import.*`, `courses.list.import`, `courses.blocks.export`/`exporting`/`exportError`.

**Bibliothèque de ressources** (`core/resources/` + `features/courses/course-resources/`) : `ResourceService` est un exemplaire de plus du patron mutable (signaux `list`/`listLoading`/`listError` refetchés à chaque entrée d'onglet, garde `#courseId` sur les patchs locaux, purge à la déconnexion) plus un signal `uploadState` (`idle|presigning|uploading|confirming|error` + `progress`, un upload à la fois). **Upload en trois temps** : POST presign (type dérivé du MIME par `resourceTypeFromMime`, repli `application/octet-stream`) → **PUT direct navigateur→S3 via `HttpClient`** — hors `environment.apiUrl`, donc l'intercepteur OIDC n'attache **pas** de Bearer (`allowedUrls`), c'est voulu ; ⚠ le header `Content-Type` doit être **strictement** le mime déclaré au presign (figé dans la signature S3) ; `reportProgress` alimente la progression — → POST confirm **sans body** (la ressource devient `available`, aucun bloc créé). Helpers purs dans `core/resources/resource.utils.ts` (`resourceTypeFromMime`, `isPdfResource` — PDF détecté par le mime `application/pdf`, **jamais un nouveau `ResourceType`** —, `resourceTypeLabelKey` — clé du badge « PDF » dédié parmi les `document`, choisie par code —, `formatBytes` — formatage maison déterministe, pas d'`Intl` — et `resourceContentUrl`, cf. Export PDF). `getDownloadUrl(courseId, resourceId, disposition = 'attachment')` : la variante `'inline'` ajoute `?disposition=inline` (affichage navigateur, consommée par `resource-view`) ; sans argument, aucun query param — la requête historique des autres consommateurs est inchangée. `CourseResources` (présentationnel + service) : liste (nom, badge type, taille, date, `pending` atténuée — bordure dashed, texte `--text-secondary`, téléchargement désactivé), upload par `<input type="file" hidden>` (input vidé après choix pour permettre le retry), **renommage inline** (FormControl public `renameControl`, Échap annule ; seul le nom affiché change, la clé S3 reste figée), **aperçu en modale** (bouton « Voir » sur les images et PDF `available` — `ResourcePreviewDialog`, `shared/resource-preview-dialog/`, `<dialog>` natif au moule resource-picker élargi à 960px, qui **embarque `CoursePreviewDocument`** plutôt que de dupliquer présignature et bypass ; son `(close)` natif remet la ressource à `null` pour **démonter l'embed** — l'effect de l'embed ne re-présigne que si la ressource change, une réouverture après expiration du TTL afficherait sinon une URL morte), téléchargement (`getDownloadUrl` puis `window.open(url, '_blank', 'noopener')` dans le composant), suppression en deux temps désarmée au blur. Le badge de type passe par `resourceTypeLabelKey` (badge « PDF » — idem dans le picker d'insertion `resource-picker-dialog`). Clés i18n sous `courses.resources.*` (dont `types.pdf`, `view`), `resourcePreview.*` et `courses.tabs.*`.

**Bibliothèque de modules interactifs** (`core/modules/` + `features/courses/course-modules/` + `shared/module-runner/` — J4, anticipé) : un module = **code HTML/CSS/JS écrit par le prof, stocké en base** (pas de S3 — décision actée, cf. Descriptions.md §5.5), exécuté dans une **iframe sandbox à origine opaque**. `ModuleService` (`core/modules/module.service.ts`) est un exemplaire du patron mutable (signaux `list`/`listLoading`/`listError` refetchés à chaque entrée d'onglet, garde `#courseId`, purge à la déconnexion) **sans upload** ; la liste est légère (`ModuleSummary`, jamais le code), le détail passe par **`getModule(courseId, id)`** — promesses partagées dans un petit cache par id, invalidé par `updateModule`/`deleteModule`/`loadList`, entrée en échec retirée (retry possible) — consommé par chaque embed affiché (un GET par module, pas par re-rendu) ; `updateModule` = PATCH partiel (renommage et/ou autosave du code par le même endpoint). `CourseModules` (onglet Modules, motif `CourseResources`) : création inline (titre → `createModule` → **redirection vers l'éditeur du module créé**), renommage inline (Échap annule), lien « Modifier », suppression en deux temps ; `(deleted)` → la page recharge le détail (blocs `module` pointeurs supprimés en cascade).

**Exécution sandbox** (`shared/module-runner/` — invariants de sécurité, ne pas « simplifier ») : `ModuleRunner` (`app-module-runner`, inputs `html`/`css`/`js`/`title`, output `moduleEvent`) compose le document via le helper pur **`composeModuleDocument`** (`module-document.ts` : **CSP `MODULE_CSP` en tête du head**, puis CSS, HTML, **bridge** injecté AVANT le JS du prof — `</script`/`</style` neutralisés en `<\/…`) et le pose **impérativement** (`iframe.srcdoc = doc` dans un effect — **jamais `[srcdoc]`** : le sanitizer Angular striperait les scripts, et on n'ajoute aucun `bypassSecurityTrustHtml` hors markdown-view). L'attribut **`sandbox="allow-scripts allow-forms allow-modals"` est statique dans le template et ne contient JAMAIS `allow-same-origin`** → origine opaque (`'null'`) : ni cookies, ni storage, ni tokens, ni DOM parent ; le **réseau sortant est BLOQUÉ par la CSP du srcdoc** (`default-src 'none'` ; autorisés : inline, **`'unsafe-eval'`** — expressions saisies évaluées type grapheur, aucune capacité nouvelle dans une iframe opaque sans réseau, résidu = self-XSS élève confiné — et assets `data:`/`blob:` ; `form-action 'none'` — décision actée, révise le « CDN autorisés » initial ; résidus assumés : la navigation par clic de lien, visible et confinée par le sandbox, et l'héritage de la CSP de la page hôte par le srcdoc — une future CSP d'en-tête posée par l'infra devra tolérer `'unsafe-eval'`). Le bridge (`oc-module:*`) fait l'**auto-resize** (ResizeObserver → `postMessage` avec `targetOrigin '*'`, obligatoire depuis une origine opaque et sans secret dans le payload) et expose **`window.ocModule.emit(name, data)`** (événements applicatifs, ex. futur score). Côté parent : listener `message` retiré au destroy, validation par **provenance** (`event.source === iframe.contentWindow` + `event.origin === 'null'`) puis par **forme** (`parseModuleMessage`, pur), hauteur clampée (`clampFrameHeight`, [80, 4000] px) bindée `[style.height.px]`. `ModuleEmbed` (`app-module-embed`, inputs `courseId`/`moduleId`) résout l'id via `getModule` (effect stale-guardé) et délègue à `ModuleRunner` — états « aucun module » / « module manquant » (motif `.course-resource--missing`) ; son hôte porte **`data-oc-module-id`** (clé de la note d'impression). Cadre DS : dashed + badge « interactif ».

**Éditeur de module** (`features/courses/module-editor/`, route `courses/:id/modules/:moduleId`, RenderMode.Client, params en snapshot) : coquille au motif block-editor — **trois Monaco HTML | CSS | JS** commutés par tabs (tablist APG, ids par compteur de module, panneaux masqués par **`[hidden]` jamais `@if`** — Monaco vit dans les trois ; refs de template `#htmlEditor`/`#cssEditor`/`#jsEditor` lues en `viewChild` pour l'application des propositions) via l'input `language` du markdown-editor, **preview live** `app-module-runner` en grid 50/50 (motif markdown-playground, empilé <900px), le tout composé avec le **chat d'édition ancré** (`app-course-chat` en mode edit, monté avec `courseId`/`moduleId` — cf. ci-dessous) dans un **espace de travail redimensionnable au motif block-editor** — grille des panes en `.module-editor__panes` (flex-basis `--editor-basis`, défaut 68 % : la colonne porte deux panes), poignée `separator` (drag + clavier, mêmes bornes 15–85), repli par `[hidden]` (bascule « Assistant » de l'en-tête, clés `courses.editor.*` réutilisées), bouton de réouverture <900px ; **hauteurs** : le pane éditeur remplit la hauteur de l'espace de travail (ligne de grille **explicite `minmax(0,1fr)`** — une ligne implicite `auto` se calerait sur le contenu et écraserait Monaco —, panneau actif `flex:1`, jamais défilé — pas de sticky : c'est le pane **aperçu qui défile dans sa propre colonne** quand le module est long) ; **Modules intégrés au markdown** (`core/markdown/course-module-ref.ts`, miroir de `course-resource-ref.ts`) : référence stable **`oc-module:<id>`**, id **validé en forme UUID** (`isModuleId`, garde de sécurité : l'id finit interpolé dans l'URL du `GET /modules/{id}` — un id forgé, path traversal compris, n'atteint jamais l'API) ; l'override des renderers `link` **et `image`** de `courseMarked` (testés AVANT `parseResourceRef` ; la syntaxe `![…]` rend le même placeholder — sans ça l'`<img src="oc-module:…">` serait vidé par DOMPurify, perte silencieuse) émet un `<span class="course-module-embed" data-oc-module-id>` inerte portant le texte du lien en repli (les `data-*` survivent à DOMPurify) ; **pas de passe async** — `markdown-view` monte un **`ModuleEmbed` par placeholder** dans le même `afterRenderEffect` que les extensions (`#mountModuleEmbeds` : `createComponent({hostElement})` + `setInput`, import dynamique **mémoïsé** de ModuleEmbed — l'iframe reste hors des chunks sans module —, garde `courseId` non nul : hors contexte cours le span reste une note inerte, **re-garde `isModuleId` sur l'attribut** — un `data-oc-module-id` peut aussi arriver par du HTML brut sans passer par `parseModuleRef` —, même stale-guard/onCleanup destructeur de refs). **Aperçu global du cours** (`features/courses/course-preview/`) : `CoursePreview` (`app-course-preview`, onglet Aperçu) rend **tous les blocs prévisualisables les uns à la suite des autres, dans l'ordre du back** — le cours tel que le verra l'élève. **Vue élève** : réponses attendues des exercices **masquées** (via `exerciseViewFromContent`, cf. `exercise-form.ts`). **Éditeur Monaco** (`shared/markdown-editor/`, CVA `string` enrobant `ngx-monaco-editor-v2`) — pièges vérifiés dans le source du wrapper, ne pas « simplifier » :
- Monaco est **servi en AMD depuis les assets** (`angular.json` copie `node_modules/monaco-editor/min/vs` → `/monaco/vs`, ~16 Mo), jamais bundlé ; `NGX_MONACO_EDITOR_CONFIG` est fourni par le composant avec un **baseUrl absolu `/monaco/vs`** (le défaut du wrapper est relatif à la page → cassé sur les routes profondes). Workers et CSS monaco s'auto-configurent depuis ce chemin.
- Le wrapper **dispose et recrée l'éditeur à chaque changement de référence de `[options]`** → options à référence stable : constante module enrichie par un `computed` sur l'input **`language`** (défaut `'oc-markdown'` ; `html`/`css`/`javascript` built-in pour l'éditeur de module — **statique par instance**, ne jamais binder un langage variable) ; le thème passe par `monaco.editor.setTheme` global (effect sur `ThemeService.theme()`, snapshot initial hors du computed), **jamais** par les options.
- Le wrapper **n'est pas SSR-safe** (touche `window`/`document` sans guard) → toute page hôte en `RenderMode.Client` + `@if (isBrowser)` dans le composant.
- Relais CVA avec **guard anti-écho** (le wrapper ré-émet la même valeur après un `writeValue`) ; `remeasureFonts()` quand JetBrains Mono finit de charger (sinon curseur décalé).
- En jsdom (specs), le loader AMD ne se charge jamais → le wrapper est **inerte par construction** : les specs pilotent les `FormControl`, jamais monaco.
- Méthodes publiques **`insertAtCursor(text)`** (insertion de ressource, cf. `markdown-field`) et **`replaceAll(text)`** (application d'une proposition HITL) : captent l'instance `IStandaloneCodeEditor` émise par `(onInit)`, `executeEdits` + `focus` — `replaceAll` édite la **plage complète entre deux `pushUndoStop`** : l'application devient UNE étape d'annulation Monaco (**Ctrl-Z la retire**, là où un `writeValue` → `setValue` de modèle VIDERAIT la pile d'undo). La mutation du modèle **passe la garde anti-écho et se propage seule** au contrôle hôte — pas de `#onChange` manuel ; no-op (`insertAtCursor`) / `false` (`replaceAll` — l'appelant se replie) tant que monaco n'est pas initialisé (SSR/jsdom). ⚠ `writeValue` porte sa PROPRE garde anti-écho (valeur déjà en place = jamais relayée au wrapper) : le `writeValue` du wrapper fait un `editor.setValue` ASYNCHRONE qui vide la pile d'annulation même à valeur identique (vérifié en vrai navigateur) — sans cette garde, les édits Monaco deviendraient inannulables au premier écho. Méthode publique `focusEditor()` (no-op masqué/SSR/jsdom) : le focus d'un élément `display:none` échoue en silence — l'hôte le rend à l'éditeur quand il le ré-affiche.

**Vue markdown réutilisable** (`shared/markdown-view/`, `app-markdown-view`) : composant présentational en lecture seule qui rend une chaîne markdown en HTML sûr via le pipeline de `course-markdown` (markdown+KaTeX synchrone puis passe Mermaid async, `effect` avec stale-guard `onCleanup`, re-rendu sur `ThemeService.theme()`, bypass DOMPurify). **C'est l'extraction du pipeline d'aperçu**, jadis dupliqué à l'identique dans `markdown-field` et `exercise-editor` ; il rend dès qu'il est **monté** (le montage est gouverné par le `@if` de l'hôte, seule la garde `isPlatformBrowser` subsiste). Consommé par `markdown-field`, l'aperçu complet d'`exercise` et `course-preview` — trois sites. Client-only. Input **optionnel** `courseId` : quand il est fourni **et** que le markdown référence des ressources, une **troisième passe** `resolveCourseResources` est chaînée sous le **même stale-guard** (après Mermaid) pour résoudre les `oc-resource:` — le composant injecte alors `ResourceService`, lit `list()` réactivement (re-rendu à l'arrivée de la bibliothèque), présigne via `getDownloadUrl`, et **ne résout qu'une fois `listLoading()` retombé** (évite un flash « indisponible »). **Gel du rendu résolu** (`#resolvedResourcesKey`, clé thème|cours|markdown) : une fois la passe ressources aboutie pour un contenu donné, l'effet sort tôt SANS relire `list()`/`listLoading()` — le `loadList()` refait par chaque page hôte traversée ne rejoue donc pas le rendu des vues encore montées (sinon : flash du HTML non résolu, re-présignature de toutes les URL et **saut de scroll du fil de l'assistant persistant** à chaque navigation) ; contrepartie assumée : une ressource devenue disponible après coup n'actualise un rendu résolu qu'au prochain changement de markdown/thème/cours. Un `effect` de **chargement défensif** (`untracked`, une fois par cours) ne charge la liste **que si aucun hôte ne l'a fait** (liste vide et pas en cours — sinon il écraserait la liste déjà présente) : en pratique ce sont les pages hôtes (`block-editor`, `course-preview`) qui chargent. En contexte cours (`courseId` non nul) il porte aussi un **bouton flottant « style de lecture »** et applique les réglages via `[style]` sur son `.course-content` (cf. **Style de lecture du rendu**).

**Style de lecture du rendu (paramétrage par cours)** (`core/courses/course-style.service.ts` + `shared/course-style-dialog/`) : le prof paramètre la typographie du rendu markdown d'un cours (taille du texte / des titres, interligne, largeur de lecture, espacement des paragraphes, police sans/avec empattement) via une modale — **propriété du cours** (pas préférence globale du lecteur), persistée côté back. `CourseStyleService` (`providedIn:'root'`) porte les réglages du **cours courant** (`settings` source de vérité + `styleVars` = `computed` des custom properties dérivées) : `load(courseId, initial)` applique `course.preview_settings` (objet enregistré, ou absent/`{}` → défauts via `clampCourseStyle`), **idempotent sur le même cours** (les sous-pages conservent une édition en vol) ; `update`/`reset` posent le signal (rendu **live**) puis poussent dans un pipeline **`debounceTime(600) → concatMap → PUT /courses/{id}/preview`** (remplacement total, **6 champs camelCase stricts**, corps relu à l'envoi, `catchError` garde le flux — motif autosave du block-editor). `HttpClient` y est injecté **`{ optional: true }`** : le service étant injecté dans le `MarkdownView` partagé, une dépendance HTTP dure forcerait tous ses hôtes (docs, playground, éditeurs) à fournir l'infra HTTP en test — sans lui (specs/SSR) le service reste fonctionnel, seule l'écriture est inactive. Helpers **purs** (même fichier) : `clampCourseStyle` (borne/valide, sert aussi de désérialiseur du JSONB) et `courseStyleVars` (mappe vers les custom properties). **Application scopée, jamais `:root`** : les composants bindent `styleVars()` en **`[style]` inline** sur leur conteneur (`markdown-view` sur `.course-content`, `course-preview` sur `#previewContent`) — scope par cours (aucune fuite vers les pages de doc) et l'inline **voyage avec le clone d'impression** → le PDF suit sans code dédié. **Unités relatives** : les dimensions dont le défaut diverge écran/papier sont des **facteurs d'échelle sans unité** (défaut 1) — écran `calc(16px × --course-font-scale)` / print `calc(11pt × …)`, idem `--course-line-scale`/`--course-para-scale`/`--course-heading-scale` (em) — un seul jeu de réglages pilote les deux médias **sans altérer aucun défaut** ; la largeur (`--course-width`, ch) est **écran uniquement** (neutralisée au print). Les défauts CSS de `.course-content` (`_tokens.scss`) valent les valeurs historiques → **zéro régression** hors personnalisation ; les titres sont **scopés** `.course-content h1..h4` (spécificité > aux règles globales `_typography.scss`, inchangées), en `em × --course-heading-scale`, famille `--font-display` conservée — seul le corps bascule serif (token `--font-serif`, Source Serif 4 @fontsource). **Modale** `CourseStyleDialog` (`<dialog>` natif au motif `MarkdownHelpDialog` : `open()/close()`, `#dialogEl`, ids ARIA par compteur de module) : `<input type=range>` enveloppés dans leur `<label>` (association implicite, pas de collision d'id entre instances) pilotant `service.update()` en direct, pilules sans/serif, footer « Réinitialiser » ; placée dans `shared/` car montée par `markdown-view` (elle injecte le service `core` comme markdown-view injecte `ResourceService`). **Deux points d'accès** : bouton flottant discret dans `markdown-view` (`.markdown-view__actions`, frère de l'impression, **visible seulement en contexte cours** — absent docs/playground) et bouton général « Style de lecture » dans la barre de `course-preview` (qui passe `[showSettings]="false"` aux markdown-view internes : un seul bouton suffit, le réglage est unique au cours ; le bouton d'impression par-bloc reste). Chargement : `course-preview` et `block-editor` appellent `load(courseId, detail.preview_settings)` dès que le détail arrive (garde `detail?.id === courseId`). Modèle : `preview_settings?` (optionnel) sur `CourseSummary`/`CourseDetail` — objet ou `{}` = jamais personnalisé (l'`import type { CourseStyleSettings }` modèle→service ne crée pas de cycle). Clés i18n `courseStyle.*`.

**Champ markdown réutilisable** (`shared/markdown-field/`, CVA `string`) : composite qui embarque les **onglets Éditeur | Aperçu** (tablist APG), l'`app-markdown-editor` (Monaco), l'**aperçu** (délégué à `app-markdown-view`, alimenté par le signal `draft` de frappe, sous `@if` sur l'onglet aperçu) et la modale d'aide. C'est l'unité que composent les éditeurs de contenu — bloc texte (une instance) et éditeur d'exercice (plusieurs : sujet + un énoncé par question ; la réponse attendue reste un textarea simple, décision produit). Composition d'un `FormControl` interne (patron `SubjectMultiPicker`) exposé **public** `control` (exception à la convention `protected` : jsdom ne peut pas taper dans monaco, les specs pilotent le contrôle) ; panneau éditeur masqué par **`[hidden]`, jamais `@if`** (un `@if` rechargerait monaco à chaque bascule) ; ids ARIA du tablist **uniques par instance** via compteur de module (**jamais** `Date.now()`/`Math.random()`). Usage **Client-only** (rendu DOMPurify + Monaco touchent `window`). `MarkdownHelpDialog` (`shared/markdown-help-dialog/`) est la modale d'aide Markdown/LaTeX/Mermaid extraite : `<dialog>` natif présentational, méthodes publiques `open()`/`close()`, ref `#dialogEl` (**pas** `#dialog` : une ref de template ne doit pas collisionner avec le signal `viewChild` `dialog`). **Éditeur de bloc** (`features/courses/block-editor/`) : **coquille-page** (en-tête, **formulaire titre/description à enregistrement explicite — tous types**, indicateur d'autosave du contenu, espace de travail redimensionnable éditeur/assistant par poignée `separator` ARIA + pointer capture, états de chargement). Le **méta** (titre/description) est un `buildBlockMetaForm` séparé, initialisé une fois depuis le bloc, bouton « Enregistrer » actif seulement si **modifié** (snapshot JSON du payload, motif page profil) ; `saveMeta` appelle `updateBlockMeta` qui n'envoie **que** le méta (jamais le `content`), pas de flush au `ngOnDestroy` (save explicite, non autosave). Le **contenu** est délégué par type : `text` → composite `MarkdownField` (`<app-markdown-field [formControl]="content" [courseId]="courseId">`), `exercise` → `ExerciseEditor` (`features/courses/exercise-editor/`, présentationnel, reçoit `[courseId]` — descendu à **chaque** `app-markdown-field` sujet/questions et à l'aperçu `app-markdown-view` pour l'insertion/résolution de ressources : **trois onglets Sujet | Questions | Aperçu complet** — tablist APG au motif `markdown-field`, cyclage clavier par `TAB_ORDER`, ids ARIA par compteur de module ; panneaux Sujet/Questions masqués par `[hidden]` jamais `@if` (Monaco vit dans les deux), panneau Aperçu en `@if` (pas de Monaco) déléguant à `app-markdown-view` le markdown concaténé `fullExerciseMarkdown` (réponses attendues exclues) — ; `[initial]` lu une seule fois, `(contentChange)` remonte chaque frappe ; **réordonnancement des questions par glisser-déposer (poignée `grip-vertical` + `cdkDragHandle`) ou clavier via `moveQuestionTo`, qui réutilise l'instance de FormGroup — invariants de `moveQuestion` préservés (ids stables J2, `@for track group`, `openGroup` par instance, snapshot `applyGeneratedIds`) — avec `*cdkDragPreview`/`*cdkDragPlaceholder` compacts pour ne pas cloner Monaco** ; helpers purs `core/courses/exercise-form.ts` ; **API d'application des propositions de l'assistant** — `applyStatement`, `applyQuestionEdit`, `applyQuestionAdd`, `applyQuestionDelete` : champs markdown écrits **via Monaco** quand il est prêt (`MarkdownField.replaceAll`, Ctrl-Z) sinon `setValue`, corrigé/ajout/suppression via le formulaire, `false` = cible introuvable, la question visée est révélée (onglet Questions, accordéon) ; champs retrouvés par refs de template `#statementField`/`#questionField` (**premier `viewChildren` du repo**, ordre DOM = ordre de la FormArray) ; helpers purs `questionIndexById`/`insertQuestionAfter`). Les blocs `document` ont une **section simple** (pas d'espace redimensionnable ni de chat — pas de Monaco) : `DocumentEditor` (`features/courses/document-editor/`, présentationnel, motif `ExerciseEditor` minimal) — picker de ressource = **`<select>` natif** (liste plate courte, pas de treeview) alimenté par les ressources `available` du cours (`ResourceService.loadList` déclenché une fois par un effect pour **tout bloc à contenu éditable** — document, mais aussi texte/exercice, dont le `markdown-field` a besoin pour le picker d'insertion et la résolution d'aperçu ; l'hôte charge, les enfants lisent le singleton), `[initial]` lu une seule fois, `(contentChange)` (légende/affichage) rejoint le pipeline d'autosave, mais `(resourcePick)` déclenche un **PATCH immédiat** `updateBlockResource` (une sélection est discrète, pas une frappe) avec état d'erreur dédié et **revert du select** (`resetResource`) sur échec ; un `resourceId` absent de la liste (ressource supprimée) retombe sur l'option vide ; **aperçu embarqué** sous le picker — `CoursePreviewDocument` monté avec `[courseId]` (input requis du DocumentEditor, fourni par block-editor) et l'éditorial **live** (légende/affichage → WYSIWYG), réactivité par **signaux miroirs posés directement** (`#selectedId` optimiste dès le pick, `#editorial` seedé en `ngOnInit`), jamais `toSignal(valueChanges)` : toutes les écritures de sync du formulaire sont en `emitEvent:false` (motif module-editor « signaux posés directement, sinon preview vide ») et `resetResource` ramène aussi l'aperçu. Les blocs `module` ont eux aussi une **section simple** : `ModuleBlockEditor` (`features/courses/module-block-editor/`, motif `DocumentEditor` sans éditorial) — `<select>` natif des modules du cours (`ModuleService.loadList` déclenché par un effect pour les blocs texte/exercice/module : picker du bloc ET picker d'insertion `oc-module:` du markdown-field), aperçu `app-module-embed`, lien « Modifier ce module » vers l'éditeur de code ; `(modulePick)` → **PATCH immédiat** `updateBlockModule` avec revert (`resetModule`) sur échec — miroir exact du flux ressource. La notice `unsupported` ne sert plus qu'aux types inconnus. **Autosave** conservé ici, dans un **pipeline unique** : `merge(content.valueChanges, frappes exercice, frappes document) → debounceTime(1500) → concatMap` (**jamais `switchMap`** : les promesses de PATCH ne sont pas annulables, une réponse périmée écraserait la plus récente), signal `saveState` (`idle|dirty|saving|saved|error` — le flux survit aux erreurs, retentative à la frappe suivante), init **une seule fois** depuis le bloc chargé et jamais réécrit depuis le signal (le patch du détail post-save ne doit pas écraser la frappe), flush fire-and-forget au `ngOnDestroy`. **Deux invariants exercice** : le payload est construit **à l'envoi du PATCH** (état courant du formulaire), jamais à l'émission, et les ids de questions générés par le back sont **réécrits après chaque save** (`applyGeneratedIds` sur un snapshot des groupes capturé à l'envoi) — sinon l'autosave suivant renverrait `id: null` et le back régénérerait des ids censés être stables à vie (contrat J2). Le contrôle `content`, le `form` de l'ExerciseEditor et le `form`/`resourceControl` du DocumentEditor sont publics (exception à la convention `protected`) : jsdom ne peut pas taper dans monaco, les specs les pilotent.

**Panneau assistant & espace de travail redimensionnable** (`features/courses/course-chat/` + layout du block-editor) : `CourseChat` (`app-course-chat`) a **trois régimes choisis par ses inputs** (`mode` computed) — `courseId` requis, `blockId`/`moduleId`/`placeholder` selon l'hôte, output `collapse` (repli). **Mode global** (aucune cible d'édition — hôte : le panneau flottant `assistant-panel`, monté une fois dans le shell et présent sur la page cours ET sur les pages d'édition, cf. section « Assistant IA du cours ») : chat câblé sur `CourseAssistantService`. **Mode edit** (`blockId` OU `moduleId` passé, sans `placeholder` — la colonne ancrée de block-editor sur un bloc TEXTE ou EXERCICE, ou celle de module-editor) : même chat, câblé sur l'instance d'`AssistantChatState` **fournie par l'hôte** (cf. « Chats d'édition ») — le panneau flottant global coexiste sur la page avec son propre état ; les appels des tools de proposition (`PROPOSAL_TOOLS` de `core/course-assistant/proposals.ts`, args bien formés) deviennent des cartes informatives titrées par tool (`app-course-chat-proposal`, input `toolName` → `courseChat.proposal.titles.*`). **Mode placeholder** (`placeholder` vrai) : la coquille « bientôt » historique, saisie désactivée — garde générique d'un hôte dont le contexte d'édition ne serait pas livré ; **plus aucun hôte ne la pose** (les quatre contextes le sont), elle reste testée pour le prochain. Piège DI : l'injection de l'état assistant est **paresseuse et par mode** (getter sur `Injector.get` — `CourseAssistantService` en global, `AssistantChatState` en edit) — un hôte en placeholder (et sa spec) n'a **aucune** dépendance IA à fournir ; toute spec montant un mode actif fournit les mocks à signaux partagés de `testing/assistant.fixture.ts` (`mockCourseAssistantService`/`mockAssistantChatState`/`mockAiCredentialsService`). Clés i18n **`courseChat.*`** (vouvoiement). Le block-editor la monte dans un **espace de travail flex à deux colonnes** (`app-markdown-field` | poignée | `app-course-chat`) — **premier layout à colonnes et premier breakpoint (`@media` 900px) du projet**. Invariants à préserver : (1) la largeur de la colonne éditeur vient du signal `editorPct` (borné 15–85 %) via la **custom property `--editor-basis`**, **jamais** un `flex-basis` inline (sinon les états CSS ne peuvent plus la surcharger) ; (2) le **repli** (`chatCollapsed`) masque chat + poignée par **`[hidden]`, jamais `@if`** (préserver la future conversation) et `.block-editor__workspace--solo` fait **grandir** l'éditeur (`flex:1`) à leur place ; (3) la poignée redimensionne via `setPointerCapture` (monaco ne vole pas les events pendant le glissé), axe dérivé du `flex-direction` réel (row → X, column → Y), clavier flèches/Home/End. Le plafond du shell `.app-main` est **relevé (1800px) pour cette seule page** (les autres pages gardent leur propre max-width ≤ 880). Sous **900px** : empilement vertical, **drag conservé** (axe Y, hauteur définie maintenue — l'IA peut être verbeuse) et un **bouton de réouverture** réapparaît sous l'éditeur (`display:none` sur desktop, où la bascule « Assistant » de la barre d'outils suffit) pour rouvrir le chat sans remonter. Libellés des contrôles sous `courses.editor.{resize,toggleChat,showChat}`.

**Chats d'édition — contextes `block_text`, `block_exercise` et `module`, flux HITL (J5)** (mode edit de `CourseChat` + `course-chat-proposal` + `core/course-assistant/{proposals,proposal-host}.ts` + briques `shared/proposal/` + revues de block-editor et module-editor) : dans l'éditeur d'un bloc TEXTE ou EXERCICE, ou d'un MODULE, le chat ancré est un vrai assistant d'édition — conversations propres à la cible ; pour un texte, l'IA **propose une réécriture complète du markdown** (`propose_block_edit`) ; pour un exercice, des **propositions par question** (décision actée — `propose_statement_edit`, `propose_question_edit`, `propose_question_add`, `propose_question_delete` : une opération par appel, une proposition à la fois, le modèle enchaîne après chaque décision) ; pour un module, des **propositions par fichier** (décision actée — `propose_html_edit`, `propose_css_edit`, `propose_js_edit`, `new_code` intégral du fichier visé, cf. « Éditeur de module »). Le flux HITL est en **interrupt/resume** (décision actée — checkpointer InMemory côté back, cf. CLAUDE.md back) : au `tool_call` `propose_block_edit`, le back FIGE le run, émet l'événement **`interrupt`** (`{tool_call_id, message_ids}` — ajouté à `KNOWN_EVENTS` du parseur) et **ferme le flux SANS `done`** ; la décision du prof **rouvre un flux SSE** (route de décision) qui reprend le run — le **résultat du tool est la décision** (acceptée/rejetée + commentaire ; le modèle peut re-proposer après un rejet commenté, nouvel `interrupt`). La proposition voyage dans les **args du `tool_call`** (complets, persistés dans `tool_calls`, refs de contenu déjà réécrites en UUID par le back).
- **État** (`AssistantChatState`) : `streamState` gagne la valeur **`awaiting`** (flux fermé sur une proposition — composer désactivé, fil live conservé, `turnActive` de `CourseChat` couvre streaming+awaiting) ; à l'`interrupt`, la proposition est posée dans le signal **`pendingProposal`** — union discriminée `AssistantPendingProposal` (`kind` `block_text` | `exercise_statement` | `exercise_question_edit` | `exercise_question_add` | `exercise_question_delete` | `module_html` | `module_css` | `module_js` ; familles typées `AssistantExerciseProposal`/`AssistantModuleProposal` par `Extract` sur le préfixe du `kind`, `MODULE_FILE_BY_KIND` → fichier `html|css|js`) produite par le helper pur **`parseProposal`** (`core/course-assistant/proposals.ts`) depuis l'appel figé de l'activité d'outils, sur les **args réécrits par le back** (`question_id`/`after_id` résolus, liens en UUID — mêmes args que dans les `tool_calls` persistés ; appel malformé = tour replié sans revue) ; **`resumeProposal({accepted, comment?})`** awaite le hook avant-tour (flush d'autosave) puis rouvre le flux (POST `…/proposals/{id}/decision`, même mécanique fetch-SSE — factorisée dans `#streamTurn`, partagée avec `sendMessage`) : la proposition est consommée à l'ouverture du flux ; sur échec d'envoi elle reste (réessayable), sauf **404** (reprise disparue — expirée/redémarrage). Envoyer un nouveau message ou changer de vue **abandonne** la proposition locale (le back purge la sienne au prochain message ou à son TTL) ; un rechargement de page la perd aussi (non ré-offerte — dette notée au TODO.md).

**Ressources de la bibliothèque intégrées au markdown** (`core/markdown/course-resource-ref.ts` — schéma **partagé par le rendu ET l'insertion**) : le markdown stocke une **référence stable** `oc-resource:<id>` (l'`id` de `CourseResource`, **jamais** l'URL présignée — TTL court, elle expirerait). Deux temps : **(1)** l'override des renderers `image`/`link` de `courseMarked` transforme un href `oc-resource:<id>` en placeholder `<img>`/`<a data-oc-resource-id>` **sans src/href** (l'attribut `data-*` survit à DOMPurify par défaut ; aucune requête réseau prématurée ; tout autre href retombe sur le rendu marked par défaut via `return false` — vérifié : `this.parser.parseInline(tokens)` pour le texte du lien) ; **(2)** `resolveCourseResources` (passe **async navigateur**, patron `renderCourseDiagrams` : DOMParser → `replaceWith` → re-sanitise) remplace chaque placeholder par l'élément choisi **selon le `type` réel** de la ressource — **image en ligne, audio/vidéo en lecteurs intégrés, PDF/autres en lien téléchargeable** —, l'URL présignée fraîche étant résolue à la volée par un callback `resolve` (une présignature par id distinct, même répété) ; ressource supprimée/`pending`/injoignable → note `course-resource--missing`. La re-sanitisation ajoute `ADD_ATTR: ['target','aria-label']` (le reste — `controls`/`loading`/`src`/`href`/`alt`/`class` — est déjà autorisé par défaut). `hasCourseResources` garde l'entrée dans la passe (comme `hasCourseDiagrams`). Cette approche DOM (vs. remplacer la chaîne markdown brute) respecte la structure : un `oc-resource:` dans un bloc de code reste du texte, jamais résolu. Helpers purs `parseResourceRef`/`resourceRefHref`/`resourceKind`/`buildResourceMarkdown` (échappe `[`/`]` du nom).

Invariants : suggestions **purgées au changement de provider/clé/base_url** (elles appartiennent à une config ; la purge efface aussi l'erreur, donc re-sonde au prochain focus — une erreur non corrigée ne re-sonde jamais en boucle), combobox absent pour `huggingface` (constante `PROVIDERS_WITH_MODEL_LISTING`, miroir du back), config insuffisante = input ordinaire + hint `models.needsConfig` (la listbox ne s'ouvre pas), tout verdict de test **effacé à la modification du formulaire** (un test réussi ne vaut plus rien pour une config modifiée), erreurs des deux sondes mappées par statut sur `settings.ai.probeErrors.*` (400 clé refusée, 422, 429, 503) — distinctes des `errors.*` de la sauvegarde. **Anti-gestionnaire de mots de passe Firefox** (vérifié en vrai navigateur) : Firefox **ignore `autocomplete="off"`** pour ses logins et greffe « Gérer les mots de passe » sur le dernier champ texte qui **précède** un `<input type="password">` (pris pour l'identifiant) — la parade effective est l'**ordre des champs** : provider → clé API → base_url → **modèle en dernier**, aucun champ texte avant le password ; ne jamais remonter le champ modèle au-dessus de la clé. Les `autocomplete` (`off` form/modèle, `new-password` clé) restent posés en complément. Côté back, les routes `/api/v1/ai/chat[...]` utilisent ce credential automatiquement quand la requête ne porte pas de config (cascade requête > credential > `AI_*`). **Pages élèves (J2)** (`features/student/` + `core/public-courses/`) : consultation sans compte, **jamais de Bearer** (la `customUrlValidation` d'`app.config.ts` exclut `/v1/public/` — même un prof connecté y passe en anonyme) et toutes en `RenderMode.Client` (**chaque** chemin a son entrée explicite dans `app.routes.server.ts` : DOMPurify sans `window` renverrait du HTML non filtré, rien ne doit retomber dans le catch-all Server). Deux régimes, **un seul jeu de composants** : `/:lang/shared/:token` et `/:lang/p/courses/:courseId` sont deux sous-arbres jumeaux qui partagent la constante **`PUBLIC_COURSE_CHILDREN`** (`app.routes.ts`) et ne diffèrent que par `data.access` (`'token'`/`'public'`, lu en snapshot par `publicAccessFromRoute`) ; s'y ajoute le catalogue prof `/:lang/p/:teacherId`. **Deux familles d'enfants, et l'ordre de déclaration est un invariant** (gardé par `app.routes.spec.ts`, qui résout les vraies routes) : d'abord les **pages pleines** à deux segments — **`modules/:moduleId`** (page dédiée d'un module, pour démontrer un module seul : ni en-tête de cours ni onglets, `max-width` 1200px) et `resources/:resourceId` (présigne puis `location.replace`), plus la **redirection** de l'ancienne page pleine `exercises/:blockId` (J2) vers `blocks/:blockId`, où l'exercice se résout désormais — `redirectTo` en **fonction**, jamais en chaîne : `@angular/ssr` résout une chaîne relative en ne retirant que le dernier segment du chemin de la route et répondrait un 302 cassé (`/…/exercises/blocks/:blockId`), alors qu'une fonction est laissée au routeur navigateur ; ses entrées `RenderMode.Client` restent dans `app.routes.server.ts` —, puis la **coquille** (`path: ''`, `StudentCourse`) et ses enfants, **une route par onglet** : Sommaire (`''`) | Ressources | Modules | Cours entier, le bloc seul vivant sous le Sommaire (`blocks/:blockId`). Sans cet ordre, `modules` (onglet) et `modules/:moduleId` (page) deviendraient ambigus. **Aucun query param** : tout l'état de navigation est dans le chemin. La coquille ne rend que l'en-tête, la barre d'onglets (**vrais liens de navigation, motif `DocsShell` — pas un tablist APG : ce sont des pages, il n'y a pas de panneau à contrôler**) et le `router-outlet` ; elle **charge le cours une fois** (elle survit aux changements d'onglet) et appelle `CourseStyleService.load`, les enfants lisant `PublicCourseService.detail()`. Deux pièges à préserver : (1) l'onglet actif est **dérivé du chemin de la route enfant** (`snapshot.firstChild.routeConfig.path`) relu à chaque `NavigationEnd` — la coquille n'étant jamais re-montée, rien d'autre ne le rafraîchirait ; (2) `StudentBlock` lit `blockId` sur le **paramMap observé, jamais en snapshot** (motif `DocsShell`) : passer d'un bloc au suivant réutilise l'instance. `PublicCourseService` est le pendant **anonyme** du patron mutable (pas d'`AuthService`, pas de purge à la déconnexion, garde `isPlatformBrowser`) : `loadCourse(access)` (idempotent — les pages pleines le rappellent sans refaire de requête —, **ne rejette jamais** : le back répond 404 quel que soit le motif, donc **un seul message d'erreur générique, pas d'oracle**), `getDownloadUrl`, `getModule` (cache Map de promesses), `contentUrl`, et il **expose `access` en signal** — les enfants de la coquille ne peuvent pas relire `data.access` (leur route parente porte un composant, ce qui coupe l'héritage de `data`), ils construisent donc leurs liens avec `publicCourseLink(lang, access, ...)`, **absolu** par nature. **Point d'articulation avec le rendu prof** : les composants de rendu partagés (`markdown-view`, `course-preview-document`, `module-embed`, `course-blocks-view`) n'injectent que les tokens `COURSE_RESOURCE_RESOLVER`/`COURSE_MODULE_RESOLVER` (`core/course-content/`) — les routes publiques y **substituent** `PublicResourceResolver`/`PublicModuleResolver` via leurs `providers`. C'est l'invariant qui garde la vue élève sans OIDC : ne jamais injecter un service prof dans `features/student/` (une spec qui oublie de fournir `COURSE_MODULE_RESOLVER` échoue d'ailleurs sur `OAuthService` — c'est le signal). Les deux résolveurs publics sont **adossés au détail déjà chargé** (`list` = `computed` sur `detail()?.resources` / `?.modules` — le back embarque les deux bibliothèques dans `PublicCourseDetail`, `ensureList` est un no-op) ; seul le **code** d'un module part en requête dédiée. Les pages : `StudentSummary` (table des matières — numéro, titre avec repli « Partie n », description, badge de type), `StudentBlock` (le bloc seul, position `n / total`, Précédent/Suivant en liens — il **réutilise `CourseBlocksView` avec un tableau à un élément**, aucun composant de rendu dédié, en **`exerciseMode="solve"`** : un bloc exercice s'y **résout** via `ExerciseView` (`shared/course-blocks-view/`) — sujet puis cartes « Question n » avec **zone de réponse** (`<textarea>` auto-grow par `field-sizing`, repli `rows`), « Marquer comme terminé », « Effacer mes réponses » en deux temps ; réponses en **localStorage seul** (`core/student/answer-storage`, clé `(courseId, blockId)`, une entrée par id de question — le J5 branchera ses soumissions sur les mêmes ids), autosave débouncée 500 ms, **flush au destroy et au changement de clé** ; storage indisponible → notice ; **tuteur IA par question** pour l'élève **connecté** — cf. paragraphe « Tuteur IA d'exercice » ci-dessous), `StudentResources` et `StudentModules` (pendants publics **en lecture seule** de `CourseResources`/`CourseModules`, sans aucune mutation ; le second est un simple **index** vers les pages de module — aucune iframe n'est montée tant qu'on n'ouvre pas un module), `StudentContent` (lecture continue, exercices en mode `preview` — cartes « Question n » sans zone de réponse — sous un CTA « Résoudre l'exercice » vers `blocks/:blockId` ; **porteuse du bouton PDF** : `PrintService` clone le DOM rendu, le `viewChild` n'existe donc que dans cet onglet) et `StudentModule` (la page dédiée). Réutilisations telles quelles : `ResourcePreviewDialog`, `ModuleEmbed`, `resourceTypeLabelKey`/`formatBytes`/`isPdfResource`. Clés i18n `student.*` ; fixtures `testing/public-courses.fixture.ts`.
